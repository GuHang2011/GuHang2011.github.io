# Reviewer guide | 博导快速阅读入口

这份入口按一位计算机专业导师第一次访问 GitHub 的阅读顺序组织。

## 30 秒 Overview

先看主页首屏是否能回答：研究什么、解决过什么问题、希望继续研究什么。简介应保持短句，链接到 3 个最有证据的项目，而不是列出完整技术栈。

建议的主页信息顺序：

1. 一句话研究定位：教育信息系统、可靠前端、数据分析与可复现工程。
2. 三个研究兴趣：工作流状态与人机交互、数据质量与建模、面向真实约束的软件工程。
3. 三个证据入口：在线案例、数据分析实验、学习笔记与复现说明。
4. 一个明确的联系方式或学术主页入口，避免在公开仓库暴露私人联系方式。

## Repositories

导师通常会先查看置顶仓库，再判断是否值得深入。每个置顶仓库应在 README 首屏给出：

- 问题和使用场景
- 个人负责的部分
- 技术路线和目录导览
- 可运行入口或在线演示
- 一个可核验的结果
- 已知限制、数据边界和复现步骤

仓库数量宜少而精。建议优先保留 4～6 个主题互补的仓库：个人主页、辅导员工作流案例、Frontend & Data Lab、一个完整的数据分析项目、一个前端交互项目，以及必要的学习笔记仓库。

## Projects

Projects 不应只是任务列表。每个项目卡片应包含研究问题、假设、数据或输入、方法、指标、当前状态、下一步和证据链接。建议使用以下栏目：

- `Research questions`：正在验证的问题
- `In progress`：当前实现或实验
- `Evidence`：演示、图表、测试和复现记录
- `Next experiments`：下一步可执行实验
- `Completed`：已完成并记录限制的工作

## 导师真正想看到的证据

- 你能否把模糊问题转成可测试任务
- 你是否理解数据切分、泄漏、指标和误差分析
- 代码是否让别人能读懂、运行和复查
- 你是否能诚实说明尚未完成的部分
- 你是否能从工程问题提炼出下一步研究问题

## 发布前底线

公开仓库不应包含真实学生信息、手机号、邮箱、学号、账号、密钥、内部地址、数据库、日志、上传文件或未经授权抓取的网页内容。每次发布前都应检查工作区和 Git 历史。
