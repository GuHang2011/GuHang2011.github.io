# React 工作流：从按钮逻辑到状态模型

整理日期：2026-10-22。本页记录本次公开学习示例的实现取舍，采用 AI 辅助编码与校对；不是过去项目经历、服务端测试或生产指标的证明。

## 先问：哪些状态变化是合法的？

把业务状态写成 `Status` 联合类型后，所有角色规则集中到 `transitions(role, status)`。负责人能提交草稿或修改稿；审核人能通过、退回或重新打开已通过任务。组件渲染的按钮与 reducer 的校验使用同一个函数，避免两份规则漂移。

`useReducer` 的价值是把一次操作作为完整事件处理。开始请求、成功、失败、冲突、刷新快照是不同事件。组件只负责定时器和焦点；模型不访问 DOM、不发请求，也不读取时钟，因此可以直接测试。

## 为什么只有一个待处理请求？

这个小示例选择每次只提交一个操作。请求进行中禁用动作和角色选择，减少重复提交；引用锁在同一轮事件中也会立即生效。代价是不同任务不能并行保存。真实看板若需要并发，可把 `pending` 改成按任务 ID 索引的映射，并逐任务取消和验证版本，而不是直接去掉锁。

## 请求取消不等于服务端回滚

重置会清除本地定时器并递增令牌。即使旧回调到达，令牌不匹配也不能修改新状态。这个例子没有网络请求。真实应用可用 AbortController 停止读取，但后端写入可能已经完成，仍需要操作 ID、幂等处理和重新读取结果。

## 冲突要让用户能恢复

版本冲突模拟“别人已修改同一条记录”。页面保持原状态，阻止继续提交，并提供刷新快照按钮。刷新只更新模拟版本，不自动重放审核决定。用户需要重新确认动作。实际后端可使用版本列或 ETag/If-Match，但必须在同一事务里检查并更新。

## 可访问性也是状态管理

任务跨列移动会重新挂载节点，原按钮因此消失。操作完成后将焦点放回目标任务，避免键盘用户回到页面起点。状态消息独立放在 `role=status` 中，不把整个应用设为播报区。减少动作偏好关闭卡片位移效果。
